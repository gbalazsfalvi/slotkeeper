# Post-quantum booking admission options

**Status** · The owner selected issuer-backed signed hold permits for v0.2. The [detailed design](../superpowers/specs/2026-11-18-slotkeeper-pqc-admission-design.md) is proposed, pending approval, and unimplemented.

Slotkeeper v0.1.0 has 15 passing local rehearsal cases. It uses scoped sessions, CSRF checks, PostgreSQL-backed admission limits, two active holds per actor and workspace, and a nonrefundable daily confirmation quota. The published release has no post-quantum cryptography. This note explores a future change for bursts of abusive hold requests and repeated capture of scarce slots. OWASP calls this booking abuse denial of inventory. [Slotkeeper v0.1.0 evidence](../evidence/v0.1.0/README.md), [OWASP API6](https://api-security.owasp.org/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/), [OWASP Automated Threats](https://owasp.org/projects/automated-threats-to-web-applications?tab=ontology)

## Options

| Option | What it demonstrates | Cost and limits |
| --- | --- | --- |
| **Issuer-backed hold permits** | A separate admission service can approve one hold intent. Booking replicas verify approval and redeem it once. Per-actor budgets address churn, and per-workspace limits protect capacity for another tenant. | Adds a service dependency for fresh holds and a time limit on grants. Actors in the same workspace can still compete for the same slot. |
| **Signed waitlist offers** | A scheduler gives the next eligible actor an expiring offer when a scarce slot opens. Offers authorize a claim, and a bounded queue can reduce polling and make allocation order explicit. | Requires rules for joining and leaving, ordering, queue capacity, offer expiry and reassignment, and recovery after lost responses. A crowded queue still needs per-actor limits. |

**Recommended first release** · Use one issuer, one fixed ML-DSA-65 permit profile, and one gated action, `POST /holds`. Two booking replicas and the existing synthetic workspaces are enough to show a real authorization boundary, conformance between providers, and one durable effect under concurrent redemption. The separate PQC Migration Lab already demonstrates signed artifacts and migration policy. Here the approval governs a live booking transaction and competes for runtime resources under load.

## Recommended hold flow

1. The same-origin ingress authenticates the current session, validates CSRF, normalizes inputs, and resolves the requested workspace against current membership. It builds an immutable principal from the session actor and the server-authorized workspace. The browser's workspace path selects a scope for the server to authorize. Browser-supplied actor, role, or workspace claim fields confer no authority.
2. The ingress calls the issuer over a private channel with a pinned, authenticated ingress service identity. The issuer accepts assertions only from that identity and only for the permitted action and audience. Its private signing key is available only to the issuer. Its PostgreSQL principal has access to its own admission ledger and a narrowly scoped capability to obtain the shared booking decision time. Booking replicas have issuer public keys and the existing booking privileges. The issuer has no reservation write privilege.
3. Charge previously unadmitted intents to an atomic rolling budget per actor within each workspace before signing. The proposed starting point is three distinct approvals in ten minutes. Reserve signing and verification capacity per workspace without imposing a shared ten-minute approval quota that members could exhaust for their peers. Store grant identity, immutable intent and key binding, nonce, and deadline. Retries can recover the live grant, and a single renewal after expiry for an uncommitted intent can reuse the original budget charge and nonce within its original window. Same-key changed input conflicts. A committed charge stands after a signing failure, cancellation, abandonment, expiry, or later capacity conflict. Tune limits against benign bursts and return `429` with `Retry-After` on exhaustion. Bound ledger retention and request rates. If the ledger, signing key, or issuer is unavailable, fresh holds fail closed with a bounded `503`. [RFC 6585, 429](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)
4. Send the permit server to server as a compact JWS. Sign the issuer, audience, actor, workspace, action, normalized fingerprint of the typed hold body, idempotency-key digest, `iat`, `exp`, and unique `jti`. Use a protected permit type and versioned profile plus protected `alg` and `kid`. Match the request to the same normalized inputs used by the application. Pin the issuer, algorithm, and key ID to local trust configuration. Reject `alg: none`, request-supplied `jwk` and `jku`, wrong types, and unexpected keys. RFC 9964 uses an empty ML-DSA context. The protected permit profile and signed claims define the application purpose. [JWS RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html), [RFC 9964 §5](https://www.rfc-editor.org/rfc/rfc9964.html#section-5), [JWT best current practices RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)
5. Bound request and permit size, parsing, and raw attempt rates before cryptography. Check the trusted caller, authorized scope, fixed key policy, and cheap claim consistency before taking a signing or verification slot. Treat decoded claims as untrusted until verification succeeds. Reserve capacity per fixture workspace under global concurrency caps for issuer and verifier. Start with immediate backpressure when crypto capacity is full. If a queue is needed, bound each workspace's queued work and wait time and schedule fairly between workspaces. Workspace caps protect specific processing budgets. Shared PostgreSQL and network capacity can still affect both tenants. [OWASP API4](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)
6. Verify the signature and exact intent binding before beginning the booking write. After acquiring the booking locks, require `decisionTime < exp` using the existing nondecreasing PostgreSQL decision clock. Issuance derives integer second timestamps from that same authority, rounding the issue time down so validity is at most 30 decision seconds. Enforce current membership, reservation quotas, and slot availability at the decision. Atomically commit redemption of the unique `(issuer, jti)`, the hold, the idempotency receipt, and the booking event. A renewed grant shares the same redemption key. Reject fresh writes with spent grants and respect the existing booking clock's documented behavior during backward wall-clock corrections. [Slotkeeper HTTP contract](../API.md), [PostgreSQL conflict handling](https://www.postgresql.org/docs/current/sql-insert.html), [RFC 9421 replay guidance](https://www.rfc-editor.org/rfc/rfc9421.html#section-7.2.2)

**Retry contract** · The PQC Migration Lab verifies every retry before consulting idempotency. A deliberate alternative for Slotkeeper is to return the current authorized state for an existing, committed receipt with the same scoped key and fingerprint, even after permit expiry or issuer outage. This path is read-only with respect to booking effects. Current session, CSRF, scope, rate admission, and authorization to read the current reservation still apply. Counters and the decision clock may advance. Test a lost success response, retry after expiry across replicas, altered input, and revoked membership. A missing receipt always requires a fresh valid permit to write. [Slotkeeper HTTP contract](../API.md)

**Trust policy** · Use a fixed trust set for the first slice. Replace it with a coordinated writer stop, drain of in-flight write transactions, and restart under the new policy. Test removal of the old key after cutover and startup with the wrong policy. Online revocation would need explicit policy-version coordination through commit to define when approvals verified under an older policy stop being usable.

## Threat boundaries

| Threat | Expected control and independent observation |
| --- | --- |
| A legitimate cookie holder repeatedly requests holds or cancels them | Bound distinct intents and in-flight work. Compare time occupied by unconfirmed holds and success for legitimate clients before and after admission. |
| An untrusted client substitutes scope or intent, or a permit is copied, altered, or presented with an older algorithm | Require current authorized binding and the pinned profile. Negative fixtures cover actor, workspace, action, body, idempotency key, audience, expiry, signature, key and version. Inspect PostgreSQL for zero new booking effects and zero redemption entries for invalid grants. |
| A grant reaches both replicas at once or expires while waiting for a lock | Verify one committed redemption, hold, receipt, and event at most. Check expiry at the post-lock decision and reauthorize concurrent replays. |
| One tenant consumes signing or verification capacity | Show bounded crypto calls and work in flight. Stress one workspace while independent legitimate requests use uncontended slots in the other. Report saturation in shared dependencies as well. |
| Issuer key, ingress, or booking worker is compromised | A stolen issuer key can fabricate approvals. Compromised ingress can assert identities it was trusted to derive. A compromised booking writer can bypass application policy within its database privileges. Key isolation and current booking checks constrain some failures. These principals form explicit trust assumptions. |

ML-DSA protects issuer approval authenticity under the algorithm's assumptions. Abuse resistance comes from admission budgets and existing access and booking controls. Many valid actors can still accumulate holds within their respective limits and consume workspace inventory. Account theft, transport security, and upstream volumetric attacks require separate controls and evidence. [NIST FIPS 204](https://csrc.nist.gov/pubs/fips/204/final)

## Java provider observation

The [recorded feasibility observation](evidence/ml-dsa-provider-smoke-2026-11-18.json) used Eclipse Adoptium `21.0.13+9-LTS`, native `SUN`, and Bouncy Castle `1.83`. Each provider verified the other's ML-DSA-65 signature. The check rejected an altered message and recorded a 3,309-byte signature. Generated keys stayed in memory. This is a provider interoperability smoke test. Benchmarks, a known-answer test, FIPS validation, and application integration remain outside that observation. OpenJDK registered ML-DSA-65 on the `jdk-21.0.13-ga` line after the original JDK 24 delivery. Pin and test the actual runtime. A 3,309-byte signature occupies 4,412 base64url characters before the JWS headers, payload, and separators. [OpenJDK 21 GA provider source](https://github.com/openjdk/jdk21u/blob/jdk-21.0.13-ga/src/java.base/share/classes/sun/security/provider/SunEntries.java), [Oracle JDK 24 changes](https://docs.oracle.com/en/java/javase/24/migrate/significant-changes-jdk-24.html), [RFC 9964 §5](https://www.rfc-editor.org/rfc/rfc9964.html#section-5)

## Evidence and next decisions

Compare published v0.1 behavior with a local 2×2 experiment varying issuance budget on/off and Ed25519/ML-DSA-65 on the same issuer and verifier topology. Keep experimental modes in the comparison harness. Freeze offered rates, seeds, replica and database limits, duration, repetitions, and acceptance criteria before evaluation. Include a benign burst, mixed churn and legitimate requests, cross-tenant saturation on uncontended slots, and a separate same-slot concurrency check.

Report legitimate success by deadline, admission false-positive rate, and unconfirmed hold occupancy in slot-minutes. Measure p95 end-to-end and stage latency, CPU time and allocation per operation where measurable, and actual transmitted bytes per path. Count false positives among legitimate, otherwise eligible intents and exclude genuine capacity conflicts from that denominator. Publish offered and observed counts and disclose any uncategorized failure. Preserve independent final-state checks. Example unmeasured gates are zero unauthorized or duplicate effects, under 1% false positives on the benign run, and quiet-tenant success under stress of at least 95% of its unstressed baseline. Set a minimum reduction in unconfirmed hold occupancy and a p95 overhead budget before the final run. These results would describe the tested workload and limits. [Java Flight Recorder guidance](https://docs.oracle.com/en/java/javase/21/troubleshoot/troubleshoot-performance-issues-using-jfr.html)

PoW and ML are deferred. A client puzzle would need evidence that the extra cost affects abusive requests more than legitimate users across device classes. If the rules leave a measurable detection gap, a shadow model could compare synthetic churn and completion signals against explicit rules at a fixed false-positive rate. Any evaluation uses known synthetic workload labels and held-out seeds. Automated bans stay outside that experiment. [Dwork and Naor](https://www.wisdom.weizmann.ac.il/~/naor/PAPERS/pvp_abs.html), [Laurie and Clayton](https://www.cl.cam.ac.uk/~rnc1/proofwork.pdf), [NIST AI RMF Measure](https://airc.nist.gov/airmf-resources/playbook/measure/)

1. Review the proposed hold permit lifetime, per-actor budget, reserved crypto limits, and the eligible workload for setting thresholds.
2. Specify the permit and receipt contracts and validate an RFC 9964 example on the pinned runtime. Then implement the issuer and one gated hold path with real PostgreSQL integration tests.
3. Run the negative state checks and the workload comparisons. Publish the updated threat model and aggregate observations, including failed or incomplete checks.
